Please revise PR #44 head f8cd86e9f9eb36388cd0152642a2f364c169defe. The new matching-token retries reintroduce a late-write race: requests A and B both observe creating and an absent object; B pauses before its put; A puts and activates; DELETE removes the object, clears the reservation and returns 204; B resumes and puts the object back. Rejecting B at D1 activation is too late. This contradicts the promised post-delete R2 absence and can leave an object outside the reserved-byte total. The same late writer can race a definite-failure reservation release. Content-addressing makes the bytes identical but does not make that schedule safe.

Keep this canary simple. Restore single-writer ownership without token-based write takeover; exact retries may reconcile an existing object but must not start another put. Resolve the earlier user-recovery concern through clear messages and an explicit Start a new save action that preserves the form but chooses a new ID. State that the old in-flight attempt may still finish; do not silently claim it was canceled. A bounded abandoned reservation is already an accepted disposable-canary trade-off. Alternatively, propose a concrete serialization mechanism that prevents all late puts, but do not add a new background service or provision extra infrastructure. Add a deterministic paused-writer/concurrent-delete test requirement and preserve the deletion retry UI fix.

For fresh-browser proof, the actual runner resets browser state per scenario and prepares server data separately (container/implementation-browser-demo.mjs and src/implementation-demo.ts). It can keep D1/R2 state between adjacent scenarios: capture the browser save/delete result, then start the immediately following fresh-context scenario against that same unchanged cloud state. No second context within one scenario is needed. Prefer that direct continuity proof over reseeding the state solely for the fresh-context screenshot. Keep one ordered collection and capture before any later data reset.

This is another design revision request, not implementation or merge approval.
