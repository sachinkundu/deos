Please revise the design in PR #44 before approval. The delete API says a failed deletion stays in deleting and a retry resumes cleanup, but the browser disables all further delete actions for deletePending rows. After a transient storage failure and page reload, the user can be stuck on “Deleting…” with no recovery path.

Keep the fix small: distinguish a request currently in flight from a persisted incomplete deletion; show an explicit Retry delete action once no local request is running, including after refresh. Preserve access to the same ID until cleanup is confirmed, even if its saved index row has already been removed. Specify how that ID remains discoverable without exposing internal operation details or calling deletion successful early. Retrying must use the existing idempotent DELETE path. Add a failure-and-retry browser/API test to the eventual implementation tasks. Do not expand into a background recovery service. Keep the approved one-screen D1/R2 scope, mandatory fresh-context proof, and proof-before-cleanup order.

The six earlier independent concerns are otherwise addressed. This requests a cloud-agent design revision, not an implementation or release approval.
